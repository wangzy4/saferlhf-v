## 2. 现在要验证什么？

主线是 **LLaVA-1.5-7B + Joint-Gradient**：在相同训练量、相同新增反馈预算下，比较主动查询和随机查询的安全性—帮助性表现及反馈效率。

安排为：

1. 共同的 **64 条启动反馈**，用于评分映射、固定特征及校准准备。
2. 独立的 **128 条开发反馈**，检查评分器质量并开展真实梯度实验 A。
3. A 通过后，使用另留置的 **256 条机制数据**开展实验 B。
4. A/B、生产训练和恢复等门禁通过，且完成训练前汇报后，才进入策略训练 C/D。

准备阶段另有 **4 次协议试标**，合计设计为 `4 + 64 + 128 + 256 = 452` 次；不是已经完成的调用数，也不自动覆盖 C/D 的在线反馈。

### 新回答和数据边界

- 192 条输入由 **96 条危险意图候选 + 96 条良性候选**构成；危险输入不意味着回答必然不安全。
- 新危险来源使用固定版本的 MM-SafetyBench 图文数据；良性来源为既有公开指令数据。文本筛查中的替换发生在生成和评分之前，256 条机制数据没有被挪用。
- 直接图文审核仍未完成；本会话再次尝试读取图片时，工具仍报告当前模型不支持图片。良性上游 family 标识、许可与跨角色隔离的接受也未完成。
- 当前 192 条仍是 **provisional**，不能因为已经投入算力而直接接受。
- 已用于开发的 MM-SafetyBench 数据不能再作为独立最终测试；独立 final test 尚未接受。

### 生成与评分保持同一口径

本地生成上限为 256 个新 token：137 条以 EOS 结束，**55 条达到长度上限且没有 EOS**。这 55 条全部保留，没有按回答内容、分数或长度筛除、重生成；后续帮助性评价必须承认截断影响。

四个评分器使用同一实际生成 token 序列，不重新分词、不补 EOS、不改写回答。这个本地生成设置 **不是已冻结的正式 RL 配方**。

## 4. 1K 与约 30K 评分器，谁更好？

**现在还不能回答。** 两档均为已完成 3 epochs 的现成评分器，本轮未重训。

L / H 只表示训练数据量档位，不表示质量高低。四组为：

| 组合 | RM | CM |
| --- | --- | --- |
| L/L | 1K | 1K |
| H/L | 约 30K | 1K |
| L/H | 1K | 约 30K |
| H/H | 约 30K | 约 30K |

目前同回答的原始分数诊断显示：

- RM 两档的 Spearman 相关为 **0.3835**。
- CM 两档的 Spearman 相关为 **0.7339**。
- 在原始零阈值下，RM 有 52/192、CM 有 39/192 条符号不同。**这不是准确率、危险率或已验证分类器的比较。**

这些数值说明评分器之间存在分歧，不能说明哪档更准确。后续只能用共同启动集拟合映射，在未参与拟合的开发集上比较 RM 的相关性和误差、CM 的 AUC / 平衡准确率 / Brier 等，再结合真实梯度证据确定共同配置。**不能根据最终哪个主动方法胜出反选评分器。**

旧验证集上的 1K / 30K 成绩仍作为历史记录保留，不替代本批新回答上的质量证据。

## 5. 梯度和发送工程，推进到哪一步？

### 梯度：已否决无依据的简化，但未完成新 A/B

使用旧缓存做的 7B pre-A 已完成 **72 次全参数 loss-only backward**，参数和 buffer 前后哈希一致，没有 optimizer step。

重复梯度差为 0，但仿射重建相对误差约 **0.79%–1.84%**，因此继续保留一般八状态方案，不接受仿射简化。该探针没有覆盖真实 PPO clip 分支切换，也不是新开发集实验 A。

### 发送：入口已写好，实际收费请求仍被阻断

- 使用独立 Sol 协议，模型 ID 固定为 `gpt-6.1-sol`；旧 Luna 标签和试标结果不能转用。
- 次数与累计美元费用上界必须在同一事务中、**网络调用之前持久预留**。
- 成功、失败、超时及崩溃后 pending 都消耗预算；零自动重试，不把 usage 当账单或退款依据。
- 发送器为单请求入口，没有批量自动续跑、自动创建新账本或换模型重试。
- 缺少有效费用依据、当前发送许可或阶段条件时不发送。具体费用额度和授权材料留在私有记录。
- 目前实现的是经审阅、精确请求绑定的全费用单次上界路径；仅凭共享余额、告警或 quota 声明不能通过。

**发送代码存在、离线测试通过，不等于服务可用性、视觉能力、实际账单或真实标签已经验收。**

## 6. 资源与旧实验状态

本次新回答生成的 GPU allocated 峰值约 **13.63 GiB**、CPU RSS 约 **17.86 GiB**；四评分器单个运行约 **68 秒**，GPU allocated 约 **13.47 GiB**、CPU RSS 约 **5.46 GiB**。这些是 GPU 推理进程的内存口径，不能说它们遵守了 CPU 准备任务的 4 GiB RSS 边界。

生成和评分结束后已释放使用的卡和协作锁。之后也按要求检查了显卡占用；**任何资源快照只代表当时，不作为下一次启动许可**。每次 GPU 启动前都重新检查空闲进程、显存、主机内存并取锁，不抢占、共享或停止他人任务，也不留自动抢卡守护进程。

旧实验状态没有被改写：正式约 30K RM/CM 与三个 epoch 状态保留；旧八卡 PPO 停于 54 步、无可恢复正式 checkpoint；旧六卡完整续训仍未验收。旧已删除 policy 权重不会因为缓存或成功标记仍在就变成可恢复资产。

## 7. 下一步及何时开始 RL

| 路线 | 下一步 | 当前门禁 |
| --- | --- | --- |
| 不依赖外部反馈的工程 | 继续生产训练接口、数值尺度、恢复与容量准备，以及输入/来源审计 | 可独立开展的本地工作继续，不因部分阻塞整体停工 |

| 机制实验 B | 留置 256 条的机制检验与回放 | A 及机制数据/反馈门禁 |
| 正式 RL C/D | 同训练量、同新增反馈预算的对照 | 真实 A/B、生产 trainer、完整恢复、容量、共同配方和相应授权 |

**正式开始 RL 前，必须先汇报真实 A/B、四组 scorer 的质量比较及拟采用的共同配置。** 当前尚没有这些完整结果，不会用工程测试通过来代替。

目前最准确的结论是：**真实生成和只读评分已落地，关键后续入口在补齐；仍处于实验准备与验证阶段，尚未证明安全性—帮助性收益或反馈效率优势。**
